# 有数 · 大学生 AI 花钱助手

> 一句话记一笔，月底心里有数。

---

## 一、名字

**有数（YouShu）**。两层意思：对账目有数，对还能撑几天有数——这正是这个产品想解决的事。工程仓库沿用 `money-mate`，避免已有链接与部署地址失效。

备选过两个：

- **余量**：更聚焦「还能撑几天」，产品感强，但学生气弱。
- **月初**：反着来——多数记账产品在月末提醒你超支，它主张月初就告诉你月底会不会慌。主张好，但名字容易被听成时间点。

最后选「有数」，因为它同时覆盖了「记清楚」和「想明白」两件事，而这个产品做的是后者。

---

## 二、是什么

一个**花钱助手**，不是记账工具。前端 Vue3，后端 FastAPI，中间一层大模型。

这个区别很重要：记账工具的目标是「把账记全」，它默认你有耐心；花钱助手的目标是「让你知道钱够不够花」，它默认你没耐心。所以它把成本压到一句话，把结论直接摆到你面前。

三件记账类产品通常不做的事：

1. **用一句话记账**——「早上地铁 5 块，中午吃饭 68」直接变成两笔待确认的账，不用选分类、选钱包、填备注。
2. **一个对话框当入口**——能记、能查、能改预算、能问余额。模型自己决定调哪个工具，用户不用先想「这件事该点哪个按钮」。
3. **主动告诉你哪里不对**——预算花得比时间快、这笔明显高于历史水平、生活费撑不到月底，打开首页就能看见，且每条都带判断依据的数字。

在线演示：`https://money-mate-8vby.onrender.com`（演示账号 `demo` / `demo123456`，免费实例 15 分钟无访问会休眠，首次打开等几秒）。

---

## 三、解决什么需求

记账类 App 的死因从来不是功能少，是**坚持不下来**。这个产品针对的是四个具体场景：

| 场景 | 真实痛点 | 怎么解 |
| --- | --- | --- |
| 每天记账 | 选分类、选钱包、填备注，一笔十几秒，坚持三天就放弃 | 一句话录入，单笔成本从十几秒压到几秒；分类口径写进提示词，不用用户自己判断 |
| 月底 | 钱花完了，但说不出花在哪。报表告诉你「餐饮 1200」，告诉不了你「比上月多花 400，主要在外卖」 | 按月聚合生成自然语言总结，配分类占比与趋势图 |
| 生活费 | 家里一次性打一学期的钱，没有预算概念，发现撑不住时已经晚了 | 设置金额与到账日，自动算「已花 / 剩余 / 日均可用 / 还能撑几天」，并在消耗进度快于时间进度时预警 |
| 对 AI 的信任 | 大模型记账最大的风险是「编数字」：一句话里两笔只记一笔、金额凭空合计 | 金额必须能在原话里找到；多笔拆开逐条确认；写操作只出草稿，点确认才入库 |

一句话概括：**降低的是「记」的成本，提高的是「看见」的概率，守住的是「不出错」的底线。**

## 四、有什么用

**对使用者**：记一笔不需要下决心，钱花在哪随时能答，超支在发生之前被提醒，而不是月底复盘时才知道。

**对产品本身**，这套设计回答了一个更普适的问题：AI 应该以什么形态进入一个已有明确流程的工具？

这个项目的答案是三条：

- **AI 是入口，不是按钮。** 早期版本有三个互不相干的 AI 接口（一句话记账、分类推荐、月度总结），用户得先想该点哪个。现在是一个对话框，模型通过 Function Calling 自己选工具。
- **写操作只出草稿。** AI 判断错了，让用户点一下的成本，远低于记错一笔再回头改。
- **没有明确线索就不调模型。** 「今天好累」这类输入直接回「请说清花了多少」，既省钱也避免模型硬猜。

## 五、技术栈

### 后端

| 技术 | 用在哪 |
| --- | --- |
| Python 3.13 / FastAPI | 全部 REST 接口，10 组路由（auth / wallets / transactions / categories / budget / allowances / stats / ai / chat / insights） |
| SQLModel（SQLAlchemy 2.x + Pydantic） | 数据模型与请求响应模型一套定义，少一层重复 |
| SQLite / MySQL | 本地与演示用 SQLite 文件；`DATABASE_URL` 一处切换 MySQL，代码不改 |
| Redis | 热点缓存 + 滑动窗口限流（Lua 脚本原子执行），未配置时自动降级为进程内实现 |
| JWT + Argon2 | 无状态鉴权与密码哈希 |
| Decimal | 金额精度，避免浮点误差在累加统计中放大 |
| Uvicorn | ASGI 服务器 |

### 前端

| 技术 | 用在哪 |
| --- | --- |
| Vue 3 + TypeScript | 7 个视图：登录、仪表盘、流水、预算、分类、年度报告、AI 对话面板 |
| Element Plus | 基础组件 |
| ECharts | 分类占比、收支趋势、年度账单 |
| Pinia | 登录态持久化与全局状态 |
| Vite | 开发与构建 |

### AI

| 技术 | 用在哪 |
| --- | --- |
| DeepSeek（OpenAI 兼容协议） | 全部模型调用 |
| Function Calling | 对话入口的 6 个工具；写操作只返回草稿，最多 3 轮工具调用 |
| JSON mode + Pydantic 二次校验 | 一句话记账的结构化输出，模型输出不合格不进库 |
| 流式输出（SSE） | 月度分析与对话逐字返回 |
| 指数退避重试 | 仅对网络抖动、超时、429、5xx 重试，4xx 直接失败 |
| MCP Server（stdio） | 把记账能力开放给 OpenClaw / Claude Desktop 等外部智能体 |

### 工程化

| 技术 | 用在哪 |
| --- | --- |
| pytest（48 项） | 38 项接口测试 + 10 项限流测试，含幂等、软删除、注入防护、多笔、洞察 |
| Vitest（14 项） | 前端 api 封装、登录 store、金额格式化 |
| GitHub Actions | 每次推送跑后端 + 前端测试 |
| Docker 多阶段构建 | 单镜像同时产出前端静态资源与后端服务 |
| Docker Compose / render.yaml | 本地编排与 Render 一键部署 |
| fakeredis | 在进程内真实执行限流那段 Lua，本地不必起 Redis 也能测生产路径 |

## 六、架构

```
Vue3 前端 ──REST / JWT──> FastAPI ──> SQLModel ──> SQLite / MySQL
                              │
                              ├──> Redis（缓存 + 滑动窗口限流）
                              ├──> DeepSeek（Function Calling / JSON mode / 流式）
                              └──> MCP Server（stdio）──> OpenClaw 等外部智能体
        AI 对话入口：模型选工具 → 草稿 → 用户确认 → 走原有写入接口
```

一个有意的分层：**AI 永远不直接写库**。模型产出的都是草稿，落库走的还是原来那批 REST 接口，所以幂等键、软删除、金额精度这些规则只需要在一个地方正确。

---

## 七、几个关键设计

**1. 多笔识别是接口契约问题，改提示词解决不了。**
「地铁 5 块 + 吃饭 68」是两笔。早期接口只能返回一笔，另一笔静默丢失——比记错更隐蔽，因为用户以为记上了。现在响应结构是 `{items, multi}`，每条带独立幂等键，前端逐条确认；其中一条金额编造时只丢那一条，不把整句话否掉。

**2. 预算预警比的是「消耗进度」和「时间进度」。**
月中花到 80% 才是问题，月末花到 80% 很正常。同样是 80%，含义完全相反，所以阈值不能只写一个数字。

**3. 异常消费要求样本量够。**
该分类至少 5 个历史样本、且金额超过 P90 的两倍才提醒，否则新用户会被误报淹没。用户点掉后 24 小时内不再出现。

**4. 限流用滑动窗口，且判断与计数原子执行。**
固定窗口在边界两侧各打满一次，实际会放过 2 倍请求。判断和计数分两步做，并发下会读到同一个旧值——所以「清理过期 + 计数 + 写入」放进一段 Lua，由 Redis 单线程执行。

**5. 效果是量出来的，不是感觉的。**
100 条标注集，准确率拆到金额、分类、钱包、日期四个字段并出混淆矩阵。改前分类 91.9%，定位到「分类口径不清」这个根因，把每个分类的边界写进提示词后到 100%。金额错和日期错严重程度完全不同，混成一个「整句准确率」看不出问题在哪。

## 八、效果

| 指标 | 结果 |
| --- | --- |
| AI 一句话记账（100 条标注集） | 类型 / 金额 / 钱包 / 日期 100%，分类 91.9% → 100% |
| 多笔输入命中 | 6/10 → 10/10 |
| 对抗样本 | 10/10 未被带跑 |
| 自动化测试 | 后端 48 项 + 前端 16 项 |
| 线上 | 已部署可访问 |

关于上面那个「100%」，要补一句诚实的话：

这 100 条是我自己标的，判分口径是我自己定的，提示词也是我调的——**同一个池子既当练习题又当考卷，100% 只能证明拟合，不能证明泛化。**

现在已经把数据集按 id 固定分桶：81 条 dev 用于调参，19 条 holdout 只在改完之后跑一次，`--split dev|holdout` 分开执行。但这 19 条在分桶之前已经被调参看过，属于历史污染；从下一轮提示词改动起，它们才算真正「没见过」。要彻底干净，得再补 20 条新用例。

**这件事本身比分数更值得讲**：指标好看不难，难的是知道这个指标值多少。

---

## 九、边界

- 演示部署在免费实例上，15 分钟无访问休眠，文件系统不持久，重部署后数据重置。
- 推荐与洞察是规则驱动，不是模型生成——规则可解释、不怕幻觉，代价是覆盖不了长尾。
- 面向个人账本，没有多端同步与家庭共享。
- MCP 走 stdio，由客户端在本机拉起，不是远程多租户服务。
